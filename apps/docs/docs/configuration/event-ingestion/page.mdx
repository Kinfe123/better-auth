# Event Ingestion

The project supports event ingestion providers, helpers, or event metadata.
## What This Is
Event ingestion describes how activity enters the product. It explains provider responsibilities, event shape, helper functions, and how ingested events become visible in dashboards, timelines, or last-seen fields.
## Why It Matters
Event Ingestion matters because it is part of how Root turns repository behavior into a usable developer or operator workflow. This page gives readers the mental model first, then uses implementation evidence as supporting context.
## Core Concepts
- event provider
- event type
- severity
- helpers
- last seen
## Typical Workflow
1. Select or implement the event provider for the host application.
2. Send normalized auth and product events through the ingestion helper.
3. Verify events appear in the UI with useful metadata and timestamps.
## Detailed Configuration Model
Event Ingestion controls behavior rather than UI copy. The important questions are what decision this configuration helps a developer make, what happens when it is absent, and what runtime behavior changes when it is enabled. This page keeps the mental model ahead of the raw files that mention the setting.

For Root, configuration usually answers one of four questions: who can access the product, where it is mounted, how it talks to auth or database state, and what optional capabilities are enabled. Each setting is documented in relation to one of those questions.
