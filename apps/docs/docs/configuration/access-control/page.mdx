# Access Control

The project has role, email, or IP allowlist and blocklist access controls.
## What This Is
Access control defines who can open and operate the administrative surface. This page explains the relationship between roles, explicit email allowlists, IP rules, and the default behavior when no rule matches.
## Why It Matters
Access Control matters because it is part of how Root turns repository behavior into a usable developer or operator workflow. This page gives readers the mental model first, then uses implementation evidence as supporting context.
## Core Concepts
- roles
- allowlist
- blocklist
- admin access
- IP rules
## Typical Workflow
1. Decide whether access is controlled by role, email, IP, or a combination.
2. Configure allow and block rules before exposing the route in production.
3. Test denied and allowed users so operators understand the security boundary.
## Detailed Configuration Model
Access Control controls behavior rather than UI copy. The important questions are what decision this configuration helps a developer make, what happens when it is absent, and what runtime behavior changes when it is enabled. This page keeps the mental model ahead of the raw files that mention the setting.

For Root, configuration usually answers one of four questions: who can access the product, where it is mounted, how it talks to auth or database state, and what optional capabilities are enabled. Each setting is documented in relation to one of those questions.

## Decision Points
- Is the setting required for every installation, or only for a specific framework, adapter, or deployment mode?
- Does the setting affect security, persistence, presentation, event tracking, or developer convenience?
- What does a developer verify after changing it?
